# Feature: Client Portal (self-service)

**Status:** Implemented (read-only self-service)

## What exists

- Client dashboard: `app/api/client/dashboard/route.ts`
- Client loan view: `app/api/client/loans/route.ts`, `app/api/client/loans/[id]/route.ts`
- Client payment history: `app/api/client/payments/route.ts`
- Client-facing dashboard UI: `app/client/layout.tsx` (header — logo, name, sign-out) + `app/client/dashboard/client-dashboard-client.tsx` (one card per loan: current balance, % paid progress bar, last payment date). Mobile-responsive — single-column by default (Tailwind's bare `grid` with no explicit columns below the `md:grid-cols-2` breakpoint), verified via Playwright viewport emulation at 320/375/768px with no horizontal overflow. Only imports shared `components/ui/*` primitives, never admin-only components.
- Session isolation from admin (client session must never carry admin privileges — `documents/ARCHITECTURE.MD` §2)
- Admin-facing account provisioning: `app/admin/clients/[id]/client-detail-client.tsx` — "Create Portal Access" / "Reset Portal Password" buttons, backed by `lib/actions/admin/clients.ts:createClientPortalAccess`/`resetClientPortalAccessPassword` and the shared `lib/services/client-portal-provisioning.ts` helper (also reused by the client-account backfill script). Generates a random password, hashes it, creates a `CLIENT` user keyed by `clients.clientNumber` (see `docs/features/auth.md`) — not the raw `clients.id` UUID, which was too long to hand out as a login — links `clients.userId`, and shows the plaintext password + login number once in a dismissable dialog — never logged or persisted in plaintext. Both actions require `ADMIN`/`SUPERADMIN` and write an audit log entry (`CREATE_PORTAL_ACCESS` / `RESET_PORTAL_PASSWORD`).
- `clients.clientNumber`: a short, unique, human-typeable login ID (`CL-0001`, `CL-0002`, ...), assigned automatically at insert time via a Postgres sequence default (`client_number_seq`, see migration `drizzle/0007_chief_rafael_vega.sql`) — no application code needs to generate or supply it, so all existing client-creation code paths get one for free. Existing rows were backfilled in the same migration.
- Deactivation cascade: `adminRepository.deactivateClient` (`lib/db/repositories/admin.repository.ts`) also flips `users.isActive = false` for the linked portal account, in the same transaction as the client deactivation.
- **Deactivated/deferred clients keep read-only portal access (2026-08-14):** `lib/auth/session.ts:getSessionUserFromToken` only enforces `users.isActive` for staff (`ADMIN`/`SUPERADMIN`) — `CLIENT`-role sessions are allowed through regardless of `isActive`, so a deactivated borrower can still log in and view their loan/payment history. This is safe because the client portal has no write surface (dashboard/loans/payments are GET-only). `deferred` never touched `users.isActive` in the first place, so deferred clients were never blocked. This reverses the original "deactivation fully revokes login" design from [[deactivate-client-revokes-portal-access]] — staff deactivation still fully locks out immediately (same session check, `role !== "CLIENT"` branch).
- **Access model (2026-08-14):** client loan-state (`clients.isActive`, `clients.deferred`) and portal login access are fully decoupled. `clients.isActive` is auto-managed by `lib/db/repositories/loan-status.repository.ts` purely from loan balance (has an active loan or not) and never gates login. Login is gated only by fields on the linked `users` row: `isRestricted` (staff-settable hard block, any role) and, in the future, `deletedAt` (account deletion — not yet built; deferred to a later task, along with a parallel staff/admin restriction workflow). A client can be `active`, `inactive`, or `deferred` and still log in and view their history.
- One-off backfill: `tools/backfill-client-accounts.ts` (bun script, run manually — not part of CI/deploy) provisions portal accounts for every existing client missing one (`userId IS NULL`), regardless of `isActive`/`deferred`/`deletedAt` — per the access model above, loan-state and deactivation never gate account eligibility, only whether a `userId` link already exists. **Fixed 2026-08-14:** the eligibility query originally also excluded `deletedAt IS NOT NULL` (and, before that, `isActive = false`) rows, so clients deactivated before ever being provisioned an account (e.g. `CL-0001`, `CL-0005`) were permanently unreachable by this script even though an existing account-holder who gets deactivated later keeps full login access — now just `isNull(clients.userId)`. Reuses `provisionClientPortalAccount`. Idempotent; supports `--dry-run`; writes generated credentials to a gitignored, mode-`0600` CSV and JSON under `tools/output/` for one-time handout — the JSON is an array of `{clientId, name, loginId, password, contactNumber, delivered}` records (`delivered` starts `false`) so a send-one-by-one script or checklist has a natural per-client unit to iterate and mark off.
